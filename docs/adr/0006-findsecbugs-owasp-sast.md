# ADR-0006 SpotBugs + Find Security Bugs for OWASP Top 10 SAST

**Status:** Decided — introduced in 1.1.7 (2026-06-17)  
**Date:** 2026-06-17  
**Context:** The project already had `dependency-check-maven` for CVE scanning of third-party libraries (OWASP A06). That covers known vulnerabilities in dependencies but not code-level web-application vulnerabilities. The question was whether to add automated OWASP Top 10 static analysis to the build.

## Decision

Add **SpotBugs + Find Security Bugs plugin** (`com.github.spotbugs:spotbugs-maven-plugin` with `com.h3xstream.findsecbugs:findsecbugs-plugin`) bound to the `verify` phase. Only bugs in the `SECURITY` category are reported (controlled by `spotbugs-security-include.xml`). Documented false positives and accepted-risk findings are excluded via `spotbugs-security-exclude.xml`. The build fails on any un-excluded finding.

## What each layer guards

| Tool | When to run | What it guards |
|---|---|---|
| `dependency-check-maven` | Explicit: `./mvnw dependency-check:check` | New CVEs in third-party libraries (A06) |
| SpotBugs + findsecbugs | Every `./mvnw verify` | Code-level security patterns (A01–A05, A08) |
| Security review skill | Pre-release / after structural changes | Design-level risks, DoS vectors, architectural decisions |

## Why findsecbugs rather than a scheduled LLM security review

Three properties matter in practice:

**1. Determinism — findsecbugs can gate the build; an LLM cannot.**  
findsecbugs produces a pass/fail signal that Maven can act on: same code, same result, every time. An LLM review is non-deterministic — it might notice a new `Math.random()` call on one run and miss it on another. A build gate requires determinism.

**2. Coverage — findsecbugs reads every line; a review reads what it is pointed at.**  
findsecbugs scans every compiled method systematically. A security review works from the architecture and the diff; it is good at design-level issues but will not exhaustively confirm that no new class anywhere in the codebase introduced an `ObjectInputStream.readObject()` call. For that kind of regression, bytecode scanning has 100% coverage by construction.

**3. Cost and speed.**  
findsecbugs adds a few seconds to `verify`. A full LLM review on every build would add minutes and API cost, making it impractical as a gate.

The LLM security review and findsecbugs are **complementary, not alternatives**: the skill audits design-level and architectural risks; findsecbugs detects line-level code patterns.

## What findsecbugs catches that a human review would have to check manually

| Risk (OWASP category) | Example pattern |
|---|---|
| Log injection (A09) | User input containing `\n` in a log statement, splitting log lines |
| Weak random (A02) | `Math.random()` or `new Random()` for a security-sensitive value |
| Hardcoded credentials (A07) | `String password = "secret"` in source |
| Weak crypto (A02) | MD5, SHA-1, DES, ECB mode |
| Unsafe XML parsing — XXE (A05) | `DocumentBuilderFactory` without disabling external entities |
| Unsafe deserialization (A08) | `ObjectInputStream.readObject()` on untrusted data |
| SSRF patterns (A10) | `new URL(userInput).openConnection()` |
| Path traversal (A01) | `Paths.get(userInput)` without validation |
| Spring endpoint exposure (A01) | `@RequestMapping` methods requiring security review |

Most of these do not currently apply to this codebase, but the scanner would catch any that slip in during future development.

## What findsecbugs cannot catch (handled by the security review skill instead)

| Risk | Why bytecode analysis cannot catch it |
|---|---|
| DoS via large upload / O(n²) CPU / OOM | Algorithmic complexity is not a code pattern |
| Unbounded concurrent runs | Threading policy, not a detectable bytecode bug |
| File namespace collisions (shared upload dir) | Design decision, not a code error |
| WebSocket topic access (`/topic/messages-<uuid>`) | Authorization policy, not detectable |
| HTTP security headers absent | Infrastructure / config, no bytecode signal |
| TLS at reverse proxy | Pure infrastructure |
| Rate limiting absent | Not a code pattern |

## Caveats specific to this project

1. **Thymeleaf templates and JavaScript are not scanned.** findsecbugs analyses Java bytecode only; XSS in templates or client-side code must be caught by code review.
2. **Lombok-generated bytecode.** Lombok's `@Data` and builder patterns generate bytecode that some SpotBugs detectors flag as false positives. These are mitigated by the SECURITY-only include filter (correctness-category bugs such as `EI_EXPOSE_REP2` are not reported).

## Filter files

- `config/spotbugs-security-include.xml` — restricts reporting to `<Bug category="SECURITY"/>`.
- `config/spotbugs-security-exclude.xml` — documents and suppresses accepted-risk findings and false positives from the initial triaged run:
  - `CRLF_INJECTION_LOGS` — accepted risk; logs are debug traces of the deduplication algorithm, not a security audit trail. Impact of log injection from a crafted RIS file is log pollution only.
  - `MODIFICATION_AFTER_VALIDATION` / `NORMALIZATION_AFTER_VALIDATION` — false positives; the "validation" detected is data-processing logic (startsWith checks, regex early-exit), not security input validation.
  - `IMPROPER_UNICODE` — false positives; case mapping and NFD normalization are applied to bibliographic text for string-similarity comparison, not for access-control decisions.
  - `SPRING_ENDPOINT` — informational marker on every `@RequestMapping` method; all endpoints reviewed in the pre-release security skill run.
  - `SERVLET_HEADER` / `SERVLET_PARAMETER` in `RateLimitInterceptor` — accepted risk; `wssessionId` and `X-Forwarded-For` are client-supplied rate-limit bucket keys. Spoofing them creates extra buckets but does not bypass authentication or authorisation. The rate limiter is best-effort DoS prevention.
  - `XSS_SERVLET` in `RateLimitInterceptor` — false positive; the response body is a Jackson-serialized hardcoded message with no user input, served as `application/json`.

## What to watch for (conditions that would reopen this)

- A future Java version (beyond 25) is not yet supported by `spotbugs-maven-plugin`; check the plugin release notes when upgrading the JDK.
- If findsecbugs adds new detectors for patterns relevant to this codebase (e.g. WebSocket injection), review the new findings before adding them to the exclude filter.
- If authentication or access-control logic is ever added, re-audit the `IMPROPER_UNICODE` and `SERVLET_PARAMETER` exclusions — they are only safe to exclude because the current app has no authentication layer.
