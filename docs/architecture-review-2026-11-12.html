Problem: Reader's readBibliographicItems is one ~340-line method; the line/continuation loop is duplicated in the Writer, and the addNormalized* methods are exposed only so tests can reach them (no locality).

Solution: One tokenizer module owns BOM, line classification and continuation state; Reader and Writer sit on top of it.

  • locality: BOM/continuation bugs fixed once
  • leverage: two callers, one interface
  • tests hit the tokenizer without temp-file setup of full items
  • catch-all RuntimeException swallow becomes visible

Problem: The 5-step rule is split across interface calls, two static calls that bypass the interfaces, an inline &&/||, and an untyped "isSameDois" map key threaded through compare(r1, r2, map).

Solution: Deepen the comparison cluster: one interface owns rule order and the DOI state; per-field comparators become internal.

  • locality: algorithm.md steps live in one place
  • interface shrinks; 4 single-adapter seams removed
  • tests cross one seam: pair in, verdict out
  • DOI rule leaves the Pages comparator
Note: the four interfaces each have one adapter (hypothetical seams). Deleting them alone only moves complexity; the win is the merged rule module.

5. Dissolve UtilitiesService into its real owners

Speculativelocal-substitutable

services/UtilitiesService.java (149): getSessionDir, resolveInSessionDir, createPath · detectBom · romanToArabic · setsContainSameString

Mass: before
interface: 8 statics
implementation: thin
session security + BOM + roman numerals + set compare, unrelated
After
session storage: dir, path rules
RIS tokenizer: BOM (see #1)
normalization: roman, set helpers

Problem: Annotated as a Spring service yet entirely static, with three unrelated concerns; the security-critical resolveInSessionDir is reached from handlers that each duplicate its exception handling.

Solution: Move each helper behind the module that owns the concern; delete the class.

  • deletion test: complexity scatters to owners
  • locality: path-security rules with session storage
  • pairs naturally with candidate 1
Not listed: the Reader/EnrichmentService/Writer call-order coupling. It sits squarely in ADR-0008 territory and is not re-opened. Also unmentioned: ADR-0001 (single mutable POJO) is respected by every candidate.

Top recommendation

Candidate 2: one Duplicate matcher module. It is the heart of the domain (the 5-step algorithm), the rule is currently scattered across four seams that have one adapter each, and a single pair-in/verdict-out interface gives the biggest gain in locality and test leverage. Candidate 1 is the close second as the largest testability win.
