DedupEndNote — Application Security Review

OWASP Top 10 & denial-of-service / resource-exhaustion assessment
Application: DedupEndNote v1.1.7 Stack: Spring Boot 4.1.0 / Java 21 Review date: 2026-07-11 Branch / commit: design @ f38de63 Method: Full source review (from scratch)

1. Executive summary

DedupEndNote is a public, no-login web tool that deduplicates bibliographic records in RIS format. Because every endpoint is reachable anonymously, the review focuses on input-handling and resource-exhaustion (DoS) risks rather than access control.

Result: no open Critical, High, Medium or Low findings. Every actionable finding from the prior review cycle has been remediated and independently re-verified against the current source. Two Info items remain open by deliberate choice (a TLS-deployment documentation note and a negligible parse-time regex observation), and one operational note applies to the session-directory reaper (shipped but disabled by default). None represents an exploitable defect in the code as written.

2. Scope & methodology

The review covered the full application source on branch design: HTTP controllers, the deduplication / comparison / normalization services, the RIS reader and writer, web and WebSocket configuration, the upload rate limiter, exception handling, application properties, and declared dependency versions. Findings were derived by direct code reading; each remediation claimed in the prior cycle was checked against the current code rather than taken on trust.

The assessment framework was the OWASP Top 10, extended with a project-specific emphasis on denial-of-service and resource exhaustion (the primary risk surface for an unauthenticated, compute-intensive tool). Dependency CVE scanning via mvnw dependency-check:check remains the authoritative pre-release gate and is noted where relevant.

3. Resolved findings (verified closed)

High Non-abortive run-timeout could permanently exhaust concurrency (self-DoS), with journal matching as the cheapest trigger
Risk (before fix) — A single CPU-bound comparison could ignore the timeout, block executor shutdown, and permanently hold a concurrency permit; repeated a few times this wedged the service with no restart-free recovery. Crafted journal strings gave an attacker a cheap way to make one comparison run long (polynomial regex backtracking).
Status RESOLVED & VERIFIED
How it is now handled
  • Guaranteed permit release. BoundedDedupRunner runs each job on a long-lived shared virtual-thread executor and acquires a bounded Semaphore. On timeout it calls future.cancel(true) and returns immediately without awaiting the worker; the permit is released in a finally that runs on every outcome (complete, busy, timeout, cancel, error). A stuck task can no longer block release. BoundedDedupRunner.java:124–158
  • Cancellation observed mid-comparison. DeduplicationService.compareSet now checks the interrupt flag inside the inner pair loop, not only between pivots, so a long run reacts to timeout/cancel within a single comparison. DeduplicationService.java:108–113
  • ReDoS trigger bounded. The abbreviation pattern is capped at the first 10 words (MAXIMUM_NUMBER_WORDS_JOURNAL_PATTERN), initialisms at 2–6 chars, and — critically — the match target is capped at 150 characters at normalization time (MAX_JOURNAL_LENGTH), so no crafted input can scale a single comparison. DefaultJournalComparisonService.java:35–37,137–191; JournalsNormalizationService.java:159,330
Medium Unbounded static pattern caches (per-JVM memory-exhaustion vector)
Risk (before fix) — Three process-global maps of compiled patterns, keyed on full (attacker-influenced) journal strings, were never evicted. Sustained uploads of many distinct journal names grew the heap without bound across runs.
Status RESOLVED & VERIFIED
How it is now handled — Replaced by BoundedPatternCache, a thread-safe LRU capped at 5,000 entries per cache. Eviction only forces recompilation on a later miss; it never changes a comparison result. BoundedPatternCache.java; DefaultJournalComparisonService.java:30–33
Low Upload rate limiter bypassable via a client-chosen key
Risk (before fix) — The limiter keyed on the client-supplied session id, so an automated uploader could mint a fresh id per request for a clean quota every time.
Status RESOLVED & VERIFIED
How it is now handled — RateLimitInterceptor keys on the client IP (first X-Forwarded-For hop when behind the documented reverse proxy, otherwise remoteAddr), not on the session id. A burst limit ≥ 2 preserves the two-file flow, and the cooldown slot is only consumed on a successful (HTTP 200) upload. RateLimitInterceptor.java:35–94
Low Per-session upload directories could accumulate on disk
Risk (before fix) — Each page load mints a session directory holding uploads and outputs; nothing in-process deleted them, so sustained use could fill the upload partition.
Status RESOLVED & VERIFIED (see operational note below)
How it is now handled — SessionDirectoryReaper adds an opt-in @Scheduled sweep that deletes session directories older than a configurable age (default 24h). Staleness is judged by last-modified time, so in-flight runs are naturally spared. SessionDirectoryReaper.java
Operational note — The reaper is disabled by default (dedup.session-reaper.enabled=false); the intended default cleanup is an external cron stop/restart. Operators who do not use that cron should enable the in-process reaper, otherwise disk can still fill over time. This is a deployment choice, not a code defect.
Low Missing HTTP security response headers
Risk (before fix) — No anti-clickjacking or MIME-sniffing headers on any response.
Status RESOLVED & VERIFIED
How it is now handled — SecurityHeadersFilter (a servlet filter, so it also covers the streamed download and error dispatches) sets X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN, and Referrer-Policy: strict-origin-when-cross-origin on every response. SecurityHeadersFilter.java

4. Open findings (accepted / informational)

Info TLS deployment expectation is undocumented
Observation — The application serves plain HTTP on port 9777. Uploads and downloads travel unencrypted unless a reverse proxy terminates TLS in front of it. This is only a real risk if the port is exposed beyond loopback without such a proxy.
Recommendation — Document the expected topology (proxy terminates TLS; the app binds loopback) in application.properties or the README. Documentation-only; no code change.
Info Parse-time field regexes have a mild backtracking shape
Observation — A few title/field patterns in the RIS reader use leading/trailing .*/.+. They run once per field (linear in record count, not on the O(n²) comparison path) against single field strings, with no nested quantifiers over overlapping input. Current amplification is negligible.
Recommendation — No action required now. Re-audit only if the record cap or field-length assumptions change. BibliographicItemReader.java:119–125

5. Controls verified effective (non-findings)

The following were examined and confirmed to be adequately handled in the current code:

AreaVerification
Path traversalresolveInSessionDir rejects null/empty names, CR/LF (log forging), absolute paths, multi-segment names, and ./.., then re-checks containment after normalization. Applied at every controller entry point.
Memory / OOM from large uploadcheckRecordCap (limit 100,000 records) runs before the file is loaded; countRecords streams the file with O(1) memory. Two-file mode sums both counts first.

WebSocket eavesdroppingThe per-page id is a 122-bit CSPRNG UUID carried only in POST params / hidden fields (never in a URL or Referer), so topic subscriptions are not practically guessable.
Injection (SQL / command / LDAP)No database, no ProcessBuilder/Runtime.exec, no LDAP. Confirmed absent.
SSRFNo outbound HTTP client anywhere in the codebase. Confirmed absent.
Error / stack-trace exposureGlobalExceptionHandler returns generic bodies and logs server-side only; favicon-style probes return a quiet 404; the Content-Disposition filename is sanitised.

7. Conclusion

The remediation cycle addressed the full set of actionable findings — one High, one Medium and three Low — and each fix was independently confirmed in the current source. The residual items are two informational notes and one deployment choice (enable the session reaper or keep the external cron cleanup). The application's DoS posture, historically its weakest area, is now backed by a defense-in-depth combination: a record cap, a bounded concurrency permit with guaranteed release, an abortive timeout with mid-comparison cancellation, a bounded pattern cache, and a capped regex target that removes the pathological backtracking case.

As standard release hygiene we recommend running mvnw dependency-check:check before each release to catch newly disclosed CVEs in transitive dependencies, and documenting the expected TLS-terminating reverse-proxy topology.
